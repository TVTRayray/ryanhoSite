`AGENTS.md`(Codex 等工具读取)和 `CLAUDE.md`(Claude Code 读取)是写给编程 agent 的说明书。它们和普通文档最大的区别是:**每次会话都会被完整载入上下文**。读者不是偶尔翻一下的人,而是每一轮都要重新读一遍的模型。

这决定了它该怎么写。

## 先算清楚成本

一份 3000 字的中文指令文件,大约占两三千个 token。会话里每一轮请求都带着它,写得越长,留给代码和对话的空间越少,真正关键的那几条规则也越容易被淹没。

所以第一条经验是:**写完量一下**。站内的[指令文件体积估算](/tools/context-size/)可以粗略算出字符数和 token 量级,在浏览器本地完成,内容不会上传。

## 写事实和约束,不写愿景

模型读得懂「代码要优雅」,但这句话几乎不改变它的行为。能改变行为的是具体、可检验的东西:

| 效果弱 | 效果强 |
|---|---|
| 注意代码质量 | 提交前运行 `npm run lint && npm test`,两者都通过才算完成 |
| 小心数据库 | 不要直接改 `migrations/` 下已有的文件,新变更另建迁移 |
| 保持风格一致 | 组件放在 `src/components/`,一个文件一个组件,用具名导出 |
| 部署时要谨慎 | 生产部署只能通过 `make deploy`,不要手动 `rsync` |

判断标准:**一条规则能不能被违反、被发现?** 不能的,大概率是可以删掉的愿景。

## 一定要写的三类信息

1. **怎么验证。** 构建、测试、检查命令,以及「什么算通过」。agent 最常见的失败不是写错代码,而是写完没验证就宣布完成。
2. **禁区。** 哪些文件是生成的、哪些目录不能改、哪些操作需要先问人。禁区比建议更值得占篇幅,因为它的代价不对称:多问一句成本很低,误删一次成本很高。
3. **仓库里看不出来的事。** 为什么用这个奇怪的依赖、哪个看起来没用的脚本其实被 CI 调用、某个 API 有什么隐藏的限流。代码能告诉 agent 的,不必再写一遍。

## 不必写的

- **目录结构的完整罗列。** agent 自己会 `ls` 和搜索,而且列表很快就会过时。只写不看就会猜错的部分。
- **语言和框架的通用知识。** 「React 组件要用 key」这类东西模型本来就知道。
- **历史记录。** 改过什么、为什么改,放在 git 提交信息里,不放在每轮都要读的文件里。

## 分层:全局、项目、子目录

大多数工具支持多层指令文件叠加,例如用户主目录下一份全局的,仓库根目录一份,子目录再各有一份。合理的分工是:

- **全局**:你个人的偏好,跨项目都成立。比如回答语言、提交信息格式、遇到不可逆操作先确认。
- **项目根目录**:这个仓库的构建、测试、部署方式,以及项目级禁区。
- **子目录**:只在那一块代码里成立的规则。比如 `packages/api/` 下关于接口兼容性的约定。

同一条规则只写在一层。重复不仅浪费上下文,还会在两处不一致时让 agent 无所适从。

## 一个检验方法

把指令文件交给一个全新的会话,只问一句:「根据这份说明,完成一次改动后你要做哪些检查?」如果它答不出你期望的那几条命令,说明关键信息被埋得太深,或者根本没写。
