这个站所在的服务器,从加 swap、升级 Node、装 Web 服务器,到签发 HTTPS 证书,都是编程 agent 通过远程命令完成的,人只做了两件 agent 做不了的事:在云控制台放行端口,在 DNS 服务商添加解析记录。

回头看,这个过程顺利的关键不是哪条命令,而是顺序。

## 第一步永远是只读采集

动手之前,agent 先用一条只读命令把机器摸了一遍:系统版本、CPU、内存、磁盘、负载、监听端口、已装的软件、内存占用最高的进程。

```sh
cat /etc/os-release; nproc; free -m; df -h /; uptime
ss -tlnp
for c in node python3 nginx caddy docker; do command -v $c; done
ps aux --sort=-%mem | head
```

这一步决定了后面所有的选型。1.9 GB 内存、没有 swap,意味着重型技术栈直接出局;只有 22 端口在监听,说明是台干净的机器,不用担心和已有服务冲突。

## 改动前,先查清楚要改的东西是怎么来的

升级 Node 之前,不是直接装新版本,而是先查旧版本的来源:

```sh
sudo -n true && echo SUDO_OK         # 能不能免密 sudo
dpkg -l | grep -E 'nodejs|npm|libnode'  # 是 apt 装的,还是 nvm 之类
npm ls -g --depth=0                   # 有哪些全局包会受影响
```

结果是:Node 来自 Ubuntu 自带的 apt 源,还有一个全局安装的命令行工具。这两点直接改变了做法:要先卸掉系统的 `nodejs`、`npm`、`libnode-dev` 再装 NodeSource 的版本,否则包冲突;那个全局工具在升级后会留在旧的全局目录里,需要提前告诉人,免得以后升级它时被旧版本遮住。

## 每一步都要有验证,而且要从外面验证

装完不等于好了。每一步之后都跑一次检查:swap 有没有出现在 `swapon --show` 里、有没有写进 `/etc/fstab`;`node -v` 是不是新版本;Caddy 配置在替换之前先跑 `caddy validate`。

站点发布后,验证分成两头:在服务器本机访问 `127.0.0.1`,和从外网访问公网地址。

## 那次差点判断错的排查

第一次从外网访问时,每个页面都返回 `302`,跳转到一个陌生的内网地址。看起来像是服务器配置错了。

但服务器本机访问是正常的 `200`。两头结果不一致,说明问题出在中间的网络上。再看跳转地址的参数,解码后是「访问网站 / 黑名单」——这是本地网络出口的上网管控设备拦截了对一个陌生裸 IP 的访问,和服务器无关。换一条网络路径访问,立刻返回 `200`。

如果只从一头验证,很可能会去改一份本来没问题的服务器配置。**两头结果不一致时,先定位是哪一段,再动手。**

## 把做不了的事明确交给人

agent 没有云控制台和 DNS 服务商的权限,这不是需要绕过的障碍,而是合理的边界。它做的是把这两步说清楚:具体加哪几条记录、每个字段填什么、为什么先用「仅 DNS」而不是代理模式。

同样重要的是**等**。DNS 还没生效时就把 Web 服务器切到域名,证书申请会反复失败,还可能撞上签发方的失败次数限制。所以顺序是:人加记录 → agent 确认公共 DNS 和权威 DNS 都已解析到 → 再切配置、申请证书。最后证书在 6 秒内签发成功。

## 总结成一张清单

1. 先只读采集,再做选型。
2. 改一个东西之前,查清它的来源和依赖者。
3. 每一步之后验证,高风险的配置先校验再替换。
4. 从两头验证;结果不一致,先定位是哪一段。
5. 权限之外的事交给人,说清楚怎么做,并等前置条件真正满足。
